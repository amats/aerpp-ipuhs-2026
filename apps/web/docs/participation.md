# Consent, surveys, withdrawal and recovery

Source paths are relative to `apps/web`. Read with [Web architecture](architecture.md), [session contracts](session.md) and [Support persistence](../../support/docs/persistence.md).

## Consent preparation and mail retries

- Resend from `confirmation_sent/auth` must use the prepared consent request in the sealed browser context in IndexedDB, preserve its ID/deadline and stage, and honor Support recipient cooldown/hourly limits. Never refresh preparation implicitly or accept a replacement email in the resend action.
- Consent preparation reads only the withdrawal boundary and pending recovery from `getParticipationState`, then saves a sealed, fixed request without advancing the screen. Full participation history remains available for consent PDF generation and debug inspection. Sending mail does not confirm consent; normal email completion does. Preserve identical retries and require explicit refresh/rechecking when the withdrawal boundary or pending deadline is no longer valid. Do not silently refresh that boundary while sending. See [renewed consent](../../support/docs/persistence.md#renewed-consent).

Correction is allowed only from `confirmation_sent/auth` and returns to consent with the previous browser identity cleared. Renew input/checks and preparation; prior mail/cloud facts remain. A server session timestamp enforces 60 seconds between mail dispatches even after changing the recipient. Identical uncertain retries reuse their original request and remain subject to Support idempotency/recipient limits.

Web allows 65 seconds for each Support mail request, covering cold starts, database work, and sequential OAuth refresh and Gmail delivery requests that each allow 15 seconds. Other authentication requests allow 15 seconds; withdrawal allows 45 seconds including acceptance and bounded cleanup. A timeout still leaves delivery unconfirmed; retry only the identical prepared request. Browser mutations show a waiting notice after 15 seconds without completing or replaying the operation. The Support confirmation page waits up to 30 seconds including the response body, then offers confirmation through the same link; its 15-second notice does not cancel the transaction. Session-status reads allow 15 seconds, and an unavailable read must not be interpreted as missing authority.

## Analysis and questionnaires

- Initial use pairs the first presented result with accepted initial answers. Firestore protects the initial attempt/browser until acceptance. Confirmed failure/cancellation before presentation can release the claim. Confirmed output loss can also release an unpresented claim after Support acknowledgement, including when Linux execution ownership proves the process ended without a terminal outcome. Missing evidence alone cannot release it. Preserve earlier attempts, errors and timing. Ordinary deletion/reanalysis is forbidden after initial presentation until acceptance; lost presented initial output requires researcher review. After acceptance, independent browsers may perform follow-up work in parallel. Reviewed administrator recovery uses fresh consent/email confirmation and preserves history. See [output-loss recovery](analysis-coordination.md#completion-retry-and-inference-retry) and [administrator destinations](../../../docs/study-operations.md#administrator-selected-recovery-destinations).
- Require an acknowledged consent-bound attempt start and its authoritative questionnaire kind before local model execution. Save that kind to the local server session and reflect it in the browser; do not repeat the upstream authentication query at analysis preparation. Terminal observations retain the original attempt identity after cancellation and cannot mutate a replacement session. Missing terminal evidence remains unconfirmed; do not infer a failed analysis or successful questionnaire from it.

Questionnaire retry preparation checks the displayed definition and seals the validated, fixed answers in one Server Function. Definition mismatch keeps answers editable; unavailable checks and sealing/storage failures remain distinct. Retries preserve the original answers and definition ID, and browser generation/storage checks reject delayed writes after replacement or cleanup.

### Definition loading and answer validation

Web loads the workspace-root `config/common/survey/survey-initial.json` and `survey-follow-up.json` when the server questionnaire module initializes and reuses the validated definitions. Every environment uses those sources. The [questionnaire definition guide](../../../docs/examples.md#questionnaire-definitions) owns schema requirements, canonical identity, archive registration and replacement during stopped operation. Admin reads archived definitions only for research ZIP creation.

The browser supplies answers and the displayed definition ID. The Web server checks that ID against the selected definition and builds `questionnaire: { kind, definitionId }` with a nested `answers` map. It includes every answerable item, using null for untouched optional answers and preserving explicit empty strings. Sections are not answers. Selected labels remain strings; Likert options come from the definition's labels without a fixed numeric range. Required items are enforced in both browser and server validation. See [participant controls](usage.md#participant-flow) for clearing choices and required/optional labels.

The required `survey_version` is human-readable definition metadata and participates in its canonical hash. Current Web requests do not send a separate `surveyVersion` field. Support rejects top-level `surveyVersion` in completion metadata and compares every metadata field on exact retries. See [exact survey retries](../../support/docs/persistence.md#exact-survey-retries).

### Submission and identical retries

`finalizeAnalysisAction` validates the server-issued completion receipt before `recordAnalysisCompletion` posts metadata to `PARTICIPANT_API_RECORD_ANALYSIS_COMPLETION_URL`. Answer submission is a separate request to `PARTICIPANT_API_SUBMIT_SURVEY_URL`, with the same `analysisId`, `consentId`, `serverId`, `clientId` and `pseudonym`. Missing identities are rejected rather than regenerated. The server-only `participant-api-headers` helper supplies the scoped Bearer credential; the browser never receives it. Require HTTP 200 and a valid shared-contract success body before advancing; malformed/empty responses or transport failures leave the outcome unconfirmed.

Every initial and follow-up analysis captures the running Web application's mirrored workspace version as required `analysisWorkspaceVersion` when the job is reserved. The completion receipt, sealed browser result and Support completion metadata retain that value. Finalization, reloads and retries use the original receipt rather than the currently running build's version. Answers join the existing `analysisQuestionnaires/{analysisId}` record without resending or replacing the analysis version; administrator recovery preserves the same metadata. No questionnaire-screen version is collected. Missing versions are invalid and cannot be inferred from a later build. See [research release provenance](../../../docs/research-release.md#release-provenance).

Normal survey entry and submission require the displayed result's analysis ID to match the validated completed analysis in the current session. The client-supplied ID is a comparison value; dispatch uses the session-owned ID. Entry rejects an already submitted result. Result restoration disables submission until validation finishes; transient entry failures retain output and answers for explicit retry. Missing-result and stale-session recovery follow [recovery decisions](recovery.md), without another inference.

Before dispatch, validate and seal the full original answer set as `pendingSurveyAnswer` in the owner-bound browser result. Sealing/storage failure prevents sending. A changed analysis, removed result or storage conflict prevents overwriting browser data and requires reload; distinguish that conflict from failure to save retry preparation. Frozen answers survive reload and uncertain responses. A reviewed initial-questionnaire recovery uses the separate owner-bound `aerpp:recovered-survey` seal without a result body, as specified in [administrator recovery](../../../docs/study-operations.md#administrator-selected-recovery-destinations).

`submittedAnalysisId` tracks accepted submission independently of result/survey navigation. An uncertain submission must be reconciled with the identical original request before ordinary deletion; withdrawal remains available. Only confirmed upstream success followed by failed session persistence returns `survey_submitted_state_write_failed`. An old survey screen that discovers an already submitted result offers reload without resealing or resending answers. Submitted answers remain read-only with the stored result until cleanup, while in-memory unsent drafts survive result/survey navigation but not reload.

## Withdrawal acceptance and receipts

Browser document requests allow 20 seconds for history and 90 seconds for original retrieval and PDF rendering. Archived-original requests from Web to Support allow 65 seconds, covering the sequential manifest and PDF reads that each allow 15 seconds, plus cold starts and authorization. Support history lookups allow 15 seconds. These limits reserve headroom between layers without guaranteeing completion during prolonged service delays.

- Reject withdrawal from `confirmation_sent` before acquiring the priority fence; Support must require an owner-matched confirmed version-2 consent, never a pending authentication record.
- Allow `completeWithdrawal` from `withdrawn/withdrawn` to retry upstream deletion without resuming participation.
- Label accepted withdrawal separately from deletion completion. Preserve pending, confirmation-unavailable, state-save-failed and browser-deletion-failed displays. Issue the withdrawal receipt on confirmed acceptance, independently of cleanup status. PDF failure offers document-only retry without resubmitting withdrawal. Keep the withdrawn session terminal across reload and cleanup confirmation; never automatically return to a fresh start. Show `support.contactEmail` as a mailto contact and explain that consent, withdrawal, plan and explanation documents remain downloadable while this browser session and reception allow access. Require durable accepted history for the session’s consent period; a saved intent alone is insufficient.

## Cleanup confirmation and restart

- Only the terminal home screen may automatically retry cleanup using the original request and email from the sealed browser context in IndexedDB, without asking for email again. Reject this session-only intent without a withdrawn session or a validated previously saved withdrawal intent (which permits recovery after a terminal-state save failure) and serialize cleanup checks without preempting active operations. Wait for session selection, then check on mount and 30 seconds after an incomplete response; the withdrawal form only reads saved state on entry and permits manual deletion retry; stop on completion, local deletion failure or unmount. Persisted server completion avoids another upstream call, but browser deletion must still succeed before showing all cleanup complete. Display the interval as the next check time, not a completion deadline.
- Keep local deletion confirmation separate from durable Support cleanup. Scheduled completion does not update `withdrawalCleanupCompleted` in Web; the original session must retry confirmation before showing cleanup complete. Its acceptance receipt does not require deletion completion. Reset may discard that retry identity while committed backend cleanup continues.
- All renewed participation after withdrawal requires an unused administrator recovery grant and fresh consent/email confirmation after cleanup, regardless of prior analysis completion. `hasCompletedAnalysis` remains retained audit evidence, never permission to restart. The withdrawn session has no ordinary restart action or receipt-acknowledgement marker.

## Reset, terminal state and reception closure

- Debug-only reset starts at `unauthenticated/start` from every previous stage, with no history lookup or authentication transfer. Revoke the captured generation before browser cleanup. Keep submitted-survey history relevant only after fresh consent/email authentication. The reception cutoff overrides all states/routes with a dedicated closed screen without changing persisted state or deleting data; do not route closure through `resetToStart`.
- Treat `withdrawn/withdrawn` as terminal. Ordinary flow actions should not move withdrawn sessions back into pre-consent steps; `/reset` is the explicit force-recovery path, and administrator recovery is the production resumption path. `resetToStart()` remains an ordinary guarded transition and must not bypass hash or terminal-state checks.

## Initial-flow completion

Support accepts initial answers and advances `studyStatus` to follow-up in the same transaction. Authentication returns the required `questionnaireKind` from current participation state, including an explicitly consumed administrator recovery grant. Neither historical survey counts nor browser preparation counts determine eligibility. Analysis attempts and submitted questionnaires remain independent research observations.

After initial-survey recovery without a browser result, acknowledged submission enters Thanks and ends the old questionnaire's frozen editing state before optional browser cleanup. Failed cleanup leaves submission accepted and offers an explicit deletion retry without resending answers. A late cleanup outcome must not change a newer screen or its inputs. Unconfirmed submissions retain the original frozen answers for exact retry.

Thanks hides the return to an unavailable result. The primary action is based on retained document input, RAM output and both browser payloads (sealed results and recovered answers), inspected in one IndexedDB snapshot: delete when data remains (or storage cannot be inspected), otherwise continue to document preparation. This also detects leftover recovered answers after a lost response or reload. The presence read grants no deletion permission; cleanup still checks its captured target. The server allows a missing browser analysis ID only at follow-up Thanks with a valid completed-analysis receipt and matching accepted-submission ID; pending submissions, stale hashes, missing authentication and active operations retain their existing guards. No historical completion or presentation observation is fabricated.
