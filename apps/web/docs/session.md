# Web session contracts

Source paths are relative to `apps/web`. Read with [Web architecture](architecture.md) and the [participation contract](participation.md).

## Expiration and cookie issuance

Each plain SessionID has one valid SHA-256 consistency hash in local SQLite. The database stores explicitly allowlisted identity, authentication and processing metadata, internal revision, operation fences and a SHA-256 digest of its random credential. Neither plaintext nor encrypted email, prepared request bodies, documents, results or survey answers are stored there. The browser authenticates with one immutable `aerpp-session-<SessionID>` HttpOnly, Secure (unless explicitly HTTP), SameSite=Lax cookie containing only a random 256-bit credential. The SessionID and hash alone never authenticate a request.

Browser IndexedDB holds SessionID and a server-sealed private context bound to generation and participant/consent identity containing email and fixed consent/withdrawal retry preparation. Only the server holds sealing keys. Context is decrypted in request memory and never written to server storage or logs. Completed results and frozen/submitted answers remain in the separate sealed browser result. An administrator-recovered initial questionnaire uses an independent browser-only `recoveredSurvey` seal, bound to consent and session generation, without a dummy result. The tab's rendered consistency stamp stays in memory; intro/survey view preferences alone use sessionStorage. Credentials never enter JavaScript storage.

Steps 1–3 are one pre-consent business state. Navigation among overview, explanation and consent returns an approved tab-local view without saving shared state or changing the hash. Result and survey views likewise share a hash. Preparing a different consent identity is an actual mutation: its PID, ClientID and consent ID are bound in authority before sending, and advance the stamp. Other tabs with older preparations are rejected before mail dispatch. Guarded operations serialize sending; once mail is accepted, pre-consent operations are rejected. Changing a valid address before sending prepares a new identity; the authentication screen also offers **メールアドレスを訂正する**, a guarded return to consent requiring renewed input/checks. Correction is unavailable after local authentication/analysis. Correction itself is immediate; server-side mail reservations retain a 60-second interval across recipient changes. Previously issued mail and accepted cloud facts are not erased; old requests cannot change the current browser identity.

Ordinary state changes atomically compare the prior revision/hash and never rewrite the credential cookie. Actions return the new stamp, and private changes additionally return sealed context and a monotonic revision. Short IndexedDB transactions store the context itself together with its revision, session generation and reset fence. Transaction completion acknowledges adoption; request success alone is insufficient. Browser adoption rejects older context responses, including after context removal. Preparation must be saved in browser storage before the external send/withdrawal; storage failure prevents dispatch. Navigation does not persist email drafts or checked consent boxes.

Read-only view navigation and result export validation use `withSessionRead`: verify the credential/hash and selected snapshot before and after the read, without acquiring a business-operation fence. The read context cannot save or destroy a session and rejects withdrawal priority or a changed snapshot. Owned document reads explicitly allow an accepted `withdrawn` session with its retained withdrawal request after the withdrawal mutation releases its fence; ordinary reads and all mutations keep the withdrawal restriction. Already-confirmed presentation uses the same read path when restoring browser results; first presentation keeps its mutation fence and upstream acknowledgement. Linux process identity permits release of an abandoned fence without changing the credential/hash. Unverifiable process fences still require administrator recovery; see [restart boundaries](recovery.md#web-process-restart).

`getSessionOptions()` uses `ttl=0` for browser seals. SQLite authority and revocation fences are retained indefinitely, independent of `SUPPORT_RECEPTION_EXPIRES_AT`. Reads remain valid after reception closure; guarded business saves still reject the closed reception. Admission renews the same random credential cookie with 400-day browser retention, without a business-state write; browser eviction or credential loss can require reauthentication. Server Component reads never write cookies. Maintenance-time period changes do not invalidate retained credentials. Pending email links retain their fixed deadline.

### Browser persistence transactions

The `aerpp-session-coordination` database owns one `coordination` / `state` record containing generation, reset attempt, context revisions/tombstones and sealed result/recovery payloads with independent opaque versions. Keeping these values in one transaction makes generation checks and writes indivisible across tabs. Transactions request strict durability and resolve only on `complete`; aborts preserve the previous record. BroadcastChannel carries only change notifications, with a focus refresh as fallback. In-memory caches support cancellation and rendering; every durable mutation checks authoritative IndexedDB state again.

Blocked database upgrades require reloading other tabs. Do not delete the database as routine cleanup: its retained generation prevents stale work from returning. Cleanup retries succeed when both payload slots are already empty in the captured generation; a changed generation or a replacement payload still prevents stale cleanup. Participant cleanup commits atomically in IndexedDB and does not depend on localStorage access. Existing version-2 state is retained; unsupported database versions require explicit site-data clearing, and retired localStorage participant values are never imported.

localStorage is reserved for discardable dismissed-notice preferences. sessionStorage holds tab-specific view preferences. Unsent consent/document drafts and displayed plaintext remain in tab memory; the credential remains in an HttpOnly cookie. IndexedDB does not make server requests, cookies or display preferences part of a browser transaction. See [analysis coordination](analysis-coordination.md#browser-result-and-answer-transactions) for result/retry commit boundaries.

## Retries and generation recovery

A stale screen or busy operation is not an invalid session. Retain browser data; stale state requires reload, while busy state permits an explicit retry after the conflicting operation ends. Admission of a confirmed invalid session revokes it, clears local/session storage, and creates a new unauthenticated session; reuse a replacement already created by another tab. An unavailable service must not trigger destructive recovery. A recent first admission whose credential cookie has not arrived is rejected as pending rather than revoked. Failed/pending initial admission offers an in-place admission retry. An already admitted screen rejected during an operation must reload before admission; it cannot silently replace active work. See [recovery decisions](recovery.md).

Persist each workflow's private prerequisite in the sealed browser context before its external effect: prepared consent before mail and the original withdrawal request before withdrawal. Persist the pending survey ID in server metadata and the original answers in the sealed browser result (or the dedicated recovered-survey seal) before survey submission. Response-loss retries preserve identity, payload and deadlines. Do not regenerate requests or infer an upstream outcome from transport failure. Prepared consent is separate from checkbox drafts and follows the [consent contract](../../support/docs/persistence.md#renewed-consent).

Explicit consent rechecking reuses an unexpired preparation with matching identity, withdrawal boundary, pending recovery ID and study generation. An expired, unconfirmed preparation requires a new consent ID and deadline after rechecking; reopening a page never extends the original request's lifetime. If recovery confirmation has already consumed the grant, verify the exact dispatched owner and reuse the saved request even after its pending deadline. This only reconciles completed confirmation; it does not renew the request or send another email. See [recovery decisions](recovery.md#decision-criteria).

Administrator recovery uses `/recovery` and the independent `/api/admin-recovery` POST handler so a queued Server Action cannot block it. The current opaque credential and hash remain mandatory; recovery discards the old private context instead of requiring it to decrypt. The checked grant ID must still match when the reset begins. A reset preempts the old operation, clears local workflow/authentication metadata, and retains the participant identity, selected grant ID and a cleanup-pending flag. No Firestore data is deleted or grant consumed by this local step. A receipt revision authorizes one atomic browser cleanup of result, frozen-answer and private-context slots, even if old payload versions changed. That revision fences late private-context responses and cancels work in other tabs sharing the scope. Repeated cleanup cannot remove newly stored work. Local analysis cancellation/failure cleanup remains independent of the recovery lookup so a Support outage cannot prevent stopping inference. Ordinary mutations and admission keep directing the participant to recovery until cleanup acknowledgement; fresh consent/email confirmation then consumes the selected grant. After a new consent is prepared, repeated reset requests preserve it. Recovery email correction and consent restart require a confirmed expired challenge; pending, confirmed or unavailable authentication retains the owner so a consumed grant can still be verified. SQLite revocation evidence and content-free audit delivery records remain retained.

Withdrawn sessions remain terminal regardless of completed-analysis history or cleanup completion. Resume only through an administrator grant and fresh consent/email authentication. Preserve the original cleanup retry identity. Scheduled Support cleanup continues independently of session loss.

`/reset` and its action are available only when `env.debugPagesEnabled` matches the debug menu guard. Its purpose is to return this site's application data to a first-visit browser state for debugging, regardless of active work. It revokes all captured browser session IDs before deleting accessible origin cookies, completes the existing participant reset transaction, and then deletes every origin IndexedDB database, including `aerpp-session-coordination` itself. It also clears all localStorage and current-tab sessionStorage entries, Cache Storage, Service Worker registrations and origin-private files when those APIs are available. A full navigation to `/` creates fresh browser state and requires consent/email authentication again; no old coordination database is retained.

Effects on concurrent processing are intentional and acceptable for this debug operation. It can interrupt analysis, authentication and questionnaire work in this or other tabs, discard documents, results and unsent or acknowledgement-pending answers, and invalidate existing screens. The reset attempt is checked before cleanup starts, but origin cleanup is non-atomic and does not coordinate with other running pages or workers. A delayed cleanup can delete data saved by a newer session or another reset; surviving pages may also recreate stores or block their deletion. Close other tabs for this site and wait for reset completion before starting fresh work. These destructive semantics are specific to debug reset, not ordinary recovery or participant actions.

Revocation is not rolled back when cookie or storage cleanup fails. Cleanup may be partial, and an open database connection can leave its deletion pending. Once the participant reset transaction has finished, cleanup failures do not reopen the coordination database to cancel it: the error notice and retry button remain available even while deletion is blocked. Close other tabs and retry (reload if needed), or delete this site's data through browser settings. Already dispatched survey or withdrawal requests may still be accepted, and browser reset does not undo those effects or erase accepted Firestore records and study eligibility. Browser history, permissions, HTTP cache and other sites' data are outside this operation. Content-free server revocation evidence remains indefinitely to prevent late admission/write resurrection. Cleanup is allowed after cutoff, but never renews authentication.

Session recovery/reset never clears Firestore study eligibility or accepted events. Losing an initial result after presentation does not authorize ordinary reanalysis or multiple initial responses. A researcher can explicitly authorize initial-document preparation, original initial-survey entry, or follow-up-document preparation, followed by fresh consent/email authentication; see [researcher recovery](../../../docs/architecture.md#participation-and-consent).

Operator-authorized environment initialization follows the [full database initialization procedure](../../../docs/study-operations.md#full-database-initialization), including the SQLite DB used by local debug Web and its selected Firestore/emulator. It is separate from `/reset`.

## Local authority resource limits

The shared SQLite authority bounds anonymous allocation across workers. [Authority constraints](../src/lib/session-authority-constraints.ts) allow an initial burst of 120 sessions, replenishing 60 per minute. Records are capped at 10,000 with 1,000 recovery slots. Unknown-ID revocation allows a burst of 60, replenishing 30 per minute. Existing/expired records remain revocable when admission is exhausted; live records and revocation fences are never evicted to admit another session.

Allocation, accounting and token consumption are transactional. Session authority and revocation fences have no automatic expiration cleanup. Transient analysis execution records contain only SessionID, a hashed attempt reference, outcome, process execution identity and expiration: running expires after the transport's 15-minute bound; missing execution evidence remains unconfirmed, not failed. These records never contain private browser context or analysis content.

Analysis prompts/results are transient RAM content described in [analysis coordination](analysis-coordination.md). They are never serialized into session metadata. Result retransmission and confirmed-failure prompt reuse require one Web Node process; restart loses them.

All workers share `aerpp-coordination/<key namespace>/server-sessions.sqlite` (directory 0700, file 0600), the private coordination file and matching key namespace. Its allowlisted metadata is not application-encrypted. Databases must match the maintained schema; startup does not migrate retained state. Unverifiable process ownership requires administrator recovery. Keep matching secrets and the volume for the study.

Consent/withdrawal retry preparation includes its pinned document-set reference. Before initial consent dispatch or first withdrawal preparation, a stale displayed set requires reload. A dispatched consent request preserves its original set and ID across deployments and uncertain retries. First withdrawal preparation validates the displayed set before acquiring its persistent withdrawal fence or preempting ordinary work; withdrawal dispatch likewise requires the saved request before taking priority. Rejection leaves current operations and document reads usable. An already saved withdrawal request keeps its original set and fence across deployments and retries. Read-only owned document history uses `withSessionRead` before and after generation, including an existing withdrawn session, without granting a new authentication route. See [document sets](../../../docs/document-sets.md).
