# Browser coordination and analysis results

Source paths are relative to `apps/web`. Read with [Web architecture](architecture.md) and the [participation contract](participation.md).

## Admission and observation

Tabs in one browser share SessionID and committed business state. There is no primary tab, competition check or awake signal. Screens, document drafts and in-memory answers need not synchronize. Ordinary mutations validate the composite state hash and operation fence; reject stale or conflicting actions with reload guidance. Releasing the admission fence alone never permits ordinary recovery/deletion/reset to clear a running, completed-but-unfinalized or unknown attempt. Confirmed unavailable output can return to preparation after Support acknowledges the loss observation, except for a presented initial result awaiting its questionnaire. Explicit cancellation can stop unfinished inference; a completion that wins the race remains protected. Result/survey navigation shares a hash. Withdrawal validates identity before taking priority; debug force reset revokes authority before browser cleanup. Reviewed Admin recovery requires participant confirmation and renewed authentication, preserving study history.

`POST /api/llm/analysis` validates named documents, checks readiness, and commits one active attempt. Readiness first checks that the operational audit queue is writable and below capacity, then checks local LM Studio model availability and current Support authentication in parallel. The local model check has a five-second timeout; Support authentication has a fifteen-second timeout to allow for cold starts. The read-only model list is bounded to 64 KiB and must contain the configured model ID. [LM Studio's model-list contract](https://lmstudio.ai/docs/developer/openai-compat/models) may include downloaded models when just-in-time loading is enabled; this check does not load a model or guarantee inference capacity. No prompts or document bodies are sent by these checks. A definite readiness failure claims no attempt, retains input, and offers return to preparation for explicit retry. Unknown admission responses continue to use observation/recovery rather than automatic reanalysis.

The active ID and its execution/restart evidence are saved in the same SQLite transaction, under the current session revision and operation fence. Support must acknowledge its consent-bound start and return the questionnaire kind fixed by that transaction before inference. Web saves that kind locally before running the model. The short admission response returns HTTP 202, the analysis ID, authoritative questionnaire kind and current session hash. The browser allows 90 seconds for admission. Support readiness allows 15 seconds; start recording allows two 15-second attempts within one 31-second budget, including the 250 ms retry wait. Admission failures after an acknowledged start may also need a 31-second terminal-recording budget. These are wait budgets, not guarantees of database completion. Status and result reads retain their separate 15-second request timeout. Status observations also carry the kind for resumed screens. LM Studio receives one `/v1/responses` request with `stream: false` and `store: false`; models, prompts and generation settings remain unchanged.

If local admission fails after Support confirms the start, Web retains the reservation and records cancellation without starting inference. Acknowledged cancellation permits explicit return to preparation and releases an unpresented initial claim; uncertain cancellation retains its original terminal request and offers **終了記録を再試行**. Explicit user cancellation likewise aborts inference without clearing the active ID or disposing the job before both Support and local coordination confirm its terminal. A completion that wins the race remains available. Authority revocation still immediately disposes retained content.

Inference runs independently of the browser connection and ordinary mutation fence. Reload, tab closure and navigation do not cancel it. Any current tab can resume read-only observation through `GET /api/llm/analysis`; `GET /api/llm/analysis/result?analysisId=...` returns the complete result only after terminal recording succeeds. Both require the current credential, composite hash and participant/consent/analysis identity. Reads neither extend retention nor mutate authority. Status polling every two seconds observes the analysis, not tab competition. Explicit cancellation, withdrawal, reset, identity replacement and reception closure stop the affected analysis job; a server watcher checks its current authority every 250 ms. Reception closure preserves participant authentication and stored business state; see [session lifetime](session.md#expiration-and-cookie-issuance).

The UI shows a spinner, elapsed time and the actual phase (waiting for LM Studio, confirming completion, or confirming recovery to preparation). Reduced-motion preferences stop rotation. Elapsed time is not model progress. Admission and status responses include elapsed milliseconds calculated on the Web server. On mount, the display starts from that value plus monotonic time since receipt, then increments once per rendered one-second timer. Polling does not correct the display clock, and delayed browser timers do not trigger catch-up jumps. Reload obtains the current server duration for the same attempt, independently of differences between browser and server clocks. Recorded analysis duration remains a separate server measurement. Failed status/result requests stop the waiting display and offer **接続を再確認**; reconnection reads the same attempt without submitting documents again. Confirmed failure stops the animation. Unknown evidence remains protected and never automatically triggers another inference.

Cancellation pauses read-only observation before sending its mutation. If admission
is still pending, first receive its bounded response and updated session token;
aborting that response would leave cancellation using the previous hash. A failed
admission response leaves explicit reconnection available instead of assuming
rollback. Aborted observation responses cannot adopt a token or invalidate the tab,
even if their bodies arrive late. Observation stays paused until cancellation is
acknowledged; completion or pending terminal recording resumes observation of the
same attempt, while an unconfirmed mutation offers explicit reconnection. Neither
path resubmits documents. Successful cancellation returns to preparation with the
tab's document draft intact.

## Memory lifecycle and limits

Document bodies, prompts and output never enter server persistence, logs, Support, Firestore or cloud fallback. The local Web Node process temporarily holds the prompt and completed output in RAM. Route Handler and Server Function bundles in that process share the same registry. Operate one Web Node process; multiple independent processes/replicas cannot serve each other's retained content, even though SQLite authority revocation is shared.

[Analysis job constraints](../src/features/llm/analysis-job-constraints.ts) bound the registry to 20 jobs and inference to 15 minutes including admission. Each terminal job expires after ten minutes; reads and retries do not refresh that deadline. The existing document/request limits still apply. JSON responses are bounded to 2 MiB and final output to 128 KiB of UTF-8 text. Incomplete, empty, invalid or oversized output cannot become a completed result. HTTP header/body wait limits align with the inference deadline.

On successful inference the prompt is discarded. Output/receipt remains available until browser storage and presentation are confirmed and the browser acknowledges receipt, or the retention deadline expires. A failed attempt retains the exact prompt and numeric document counts for an explicit inference retry. Disposal clears retained references, timers and authority watching and aborts any outstanding inference. Revocation also disposes retained content. Process restart loses all RAM content; durable metadata never reconstructs prompts or results.

## Completion retry and inference retry

Never render pending output. Finalize metadata, store the sealed owner-bound result in browser IndexedDB, and confirm the Firestore presentation event before exposing output or Word export. The idempotent first presentation timestamp grants permission to display; it is not proof that the participant read the screen. A crash between recording and rendering cannot be observed exactly.

Freeze terminal outcome and timestamps before any fallible storage or transport. Commit the local checkpoint and durable audit together on one SQLite connection before remote delivery; remember confirmed remote acceptance while retrying an unfinished local confirmation. Queue cleanup is best-effort after those confirmations and cannot undo success. All storage/transport failures leave the same terminal request retryable; concurrent retries share one recording operation.

If terminal recording fails after successful inference, preserve output and offer completion retry with the exact original terminal payload and timestamps. Failed or cancelled inference with unacknowledged terminal delivery reports `termination_pending` and offers **終了記録を再試行** with that same frozen request. Only acknowledgement restores confirmed failure/cancellation and its existing recovery choices; unknown evidence without a frozen request cannot use this retry. Retries coalesce, respect current ownership and never extend retention. Metadata finalization, browser storage and presentation failures likewise offer completion retry without another model request. Reload can retrieve the RAM result within its deadline, including after metadata finalization committed but browser storage failed. Already saved results restore from browser storage and reconfirm presentation. After storage and Firestore presentation succeed, expose the result without waiting for RAM cleanup. Send `DELETE /api/llm/analysis/result?analysisId=...` in the background with a 15-second timeout, outside the serialized Server Function dispatcher. The server requires the current finalized and presented analysis ID. A failed or stalled acknowledgement leaves content to expire naturally; late cleanup responses never adopt a session token or invalidate the displayed screen.

**解析を再試行** is separate: only a current, confirmed `failed` attempt with its retained prompt can start a new analysis ID. The server reuses the original prompt and numeric counts without receiving new document text, checks the current hash and conflicting/completed evidence, and obtains a fresh Support start acknowledgement. There is no automatic model retry. Cancelled, unknown or completed attempts cannot use this operation. After expiry, a confirmed failure can explicitly return to document preparation; a reload has lost that tab's draft.

For unavailable output, status reports recovery eligibility when the RAM job is absent and durable local metadata confirms completion or demonstrates that its Linux execution process has ended. The UI automatically requests return to document preparation. The server rechecks stage, authentication, current hash, analysis ID, missing RAM and the initial-presentation boundary. Follow-up loss may recover after presentation; a presented initial result awaiting its questionnaire requires researcher review. Support must acknowledge an owner-bound `unavailable` observation before local analysis identifiers are cleared. Its transaction adds `resultUnavailableAt` and the loss reason without replacing the original start, terminal timing or completion metadata; it releases an unpresented initial claim and blocks subsequent metadata/presentation for that abandoned attempt. A late terminal acknowledgement may still preserve the original execution facts. Retain the document draft if this tab still has it; reload has lost that draft. Do not automatically infer again. After a failed recovery, explicit **接続を再確認** rereads the same attempt and its current recovery eligibility before another recovery request. Stale session state still requires reload; transport failure alone does not. Unknown execution outcomes remain unconfirmed even when abandoned ownership permits output-loss recovery. Unverifiable ownership requires administrator review. Browser/server session recovery does not independently change Firestore eligibility. See [study operations](../../../docs/study-operations.md) for the three administrator destinations.

The audit outbox initially waits 30 seconds and is polled every 15 seconds. Each leased notice has one 15-second HTTP attempt and a 60-second lease. Redelivery uses exponential backoff from five seconds to five minutes, with per-notice jitter and any longer Retry-After. Authentication failures retain the notice and wait at least five minutes so corrected credentials can resume delivery; invalid requests and conflicts remain blocked for operator review. A lease expiry does not prove remote rollback. Exact receiver-side identity/outcome matching handles duplicate and late requests. The capacity check before analysis does not reserve future disk space or an outbox slot. Failed registration retains the immutable RAM request for explicit retry; restart cannot reconstruct unregistered outcomes or output. Audit delivery never grants display permission or changes eligibility.

## Transport choices

Route Handlers own bounded document admission, read-only status/result retrieval and bounded background RAM acknowledgement. Short Server Functions own inference retry, completion-record retry and guarded recovery to document preparation. This keeps polling separate from browser-serialized Server Function mutations and avoids passing documents through their default body limit. Every mutation retains the same session/hash/operation guards. Slow browser mutations and analysis admission show a waiting notice after 15 seconds without ending the request or releasing its fence. HTTP retries retain one total budget, honor Retry-After, and stop before starting another attempt that cannot fit; cancellation also interrupts backoff. Body-read failures do not automatically replay submitted requests.

## Output and browser payload budgets

The configured local model has a 32,768-token input-plus-output context. Byte
budgets are resource limits, not tokenizer estimates; document grapheme limits do
not guarantee that an input fits that context, and the application never silently
truncates documents or changes model generation settings.

Web accepts at most 128 KiB of UTF-8 result text and 2 MiB of Responses JSON. A
result plus an API-valid frozen questionnaire (at most 200,000 JSON bytes) fits
within the 1 MiB browser-seal envelope budget even with six-byte JSON escaping of
every result byte, leaving over 60 KiB for owner/completion metadata. The result
writer verifies the actual serialized envelope before encryption and the actual
seal afterward. Browser-seal readers share the derived Base64/encryption bound;
Server Actions allow 2 MiB including request framing. Recovered-survey retries use
the same envelope/seal limits. Existing valid browser seals can still be read and
resealed within those budgets. Browser storage failures remain explicit and keep
retry/recovery choices; capacity limits do not establish browser quota availability.

## Browser result and answer transactions

Result writes and normal/recovered questionnaire preparation first read an IndexedDB snapshot (generation plus payload version), then perform sealing/unsealing requests outside the transaction. A short read-write transaction checks the same generation, absence of reset and unchanged payload version before replacing the complete sealed value. Survey dispatch follows transaction completion. Two tabs preparing different answers from the same snapshot cannot both commit: the loser must reload/reconcile, and retries restore the winner's frozen answers. Opaque versions also reject a stale write when intervening writes happen to restore the same bytes.

Completion re-saves inspect an existing sealed result before replacement. Frozen
answers, confirmed submission or a different analysis require reload through the
normal restoration path; a plain RAM result cannot replace that progress even
when it predates the write's snapshot. An unavailable or malformed inspection
preserves the saved value and permits explicit completion retry. A plain result
for the same analysis may still be saved again, including after presentation
failure. The final generation/version comparison also rejects questionnaire
freezing or other replacements during inspection and sealing.

For accepted withdrawal, new-analysis preparation, flow reset and recovery, capture both result and recovered-answer versions before the server transition. After acceptance, clear both payloads in one transaction only if those versions and generation still match; a repeated cleanup can also acknowledge already-empty slots in the same generation. A late response cannot delete a newer tab's replacement. A server commitment and browser cleanup are separate facts: failed/aborted cleanup reports incomplete local deletion and preserves an explicit retry. Never hold a browser transaction across HTTP, encryption, model execution or UI interaction, and never treat an IndexedDB request's success as a committed retry record.

Debug force reset is the deliberate exception to preserving concurrent browser work. It clears private contexts and replaces the generation before deleting every browser database, including coordination, and reloading to first-visit state. This origin cleanup is non-atomic and can interrupt active work or delete data saved by a newer session while cleanup was pending. Close other tabs and wait for completion before starting fresh work. Accepted server records and study eligibility remain intact; see the [reset contract](session.md#retries-and-generation-recovery).

After acknowledged recovered-survey submission, optional draft cleanup compares the original sealed envelope before deleting with the current generation/version guard. A different draft is retained and cleanup remains unconfirmed; an already empty slot can acknowledge deletion. Acceptance and the tab's old frozen-answer state do not depend on this cleanup. Thanks reads both payload-presence flags in one short transaction, and its explicit deletion action uses the guarded two-payload cleanup above. These display and cleanup retries do not resubmit answers or add durable server state.
