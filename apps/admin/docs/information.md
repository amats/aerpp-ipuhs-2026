# Admin information management

This guide owns notice behavior, concurrent edits, drafts and authorization. Read [Admin setup](../README.md) and [persistence ownership](../../../packages/firestore/README.md) alongside it.

## Information management

Notice text preserves authored line breaks and indentation in Admin and in participant-facing Web notices. Long notice text wraps within the available width and is displayed as plain text.

`/information` lists, creates, edits and deletes environment-wide notices, independent of the fixed server scope. Every read and mutation requires the existing Admin session. Content, tone (`info`, `warning`, `error`) and expiry use the shared participant API constraints; the expiry form accepts IANA time zones (default `Asia/Tokyo`) and converts local input to UTC for storage. Changing the zone reinterprets the entered wall-clock time; editing converts the stored instant into the selected zone. DST gaps are rejected, and ambiguous repeated times require explicit UTC input. The list displays UTC timestamps. Creation timestamps and IDs survive edits. Update-time preconditions reject stale edits/deletes, including TTL deletion races; reload and explicitly select the latest record before retrying. Failed requests preserve the input; check the list before retrying an ambiguous creation.

Notice editing moves focus to the edit form, including when started from the bottom of a long list. Notice validation and operation failures receive keyboard focus and scroll into view, while preserving the draft for correction, including the displayed tone selection. Successful saves clear the accepted draft and restore the default tone; successful operations use a polite status message. A conflicting edit refreshes the saved notice and retains all draft fields. The operator reviews the saved content, tone and expiry, then explicitly continues with the draft or discards it to load the saved version. Further concurrent updates still reject the save; deleted notices cannot be recreated by a stale edit. Finish or cancel the current edit before selecting another notice. A failed list refresh keeps the same editor and draft mounted; saving remains blocked until the list can be read again.

Unsaved notice fields, selected record/version, operation status and feedback remain in the current page's memory during internal navigation, including browser Back/Forward. Returning to the form preserves the draft; an outstanding operation keeps it locked until the result is known. Drafts are not stored in browser storage or sent to the server before saving. Switching from a dirty new draft to an existing notice, discarding an edited draft or loading a conflicting saved version requires confirmation. Signing out also asks before discarding unsaved changes and only starts sign-out after acceptance. Reloading or closing the tab uses the browser's native leave-page confirmation while changes are unsaved, even from another Admin page. This is an in-memory safeguard, not recovery after browser termination.

Deletion confirmation retains the record version selected when it was opened, including across list refreshes. If that version has changed or disappeared, confirmation fails, closes and refreshes the list. Review the current record and select delete again to confirm the new version.

The shared [Firestore repository](../../../packages/firestore/README.md) owns persistence; the server-only adapter retains project selection and credentials. Web fetches on mount and remembers dismissed IDs: editing does not redisplay a dismissed notice. Add a new notice for a new announcement. Expired records remain visible until asynchronous TTL deletion; neither the existing Support API nor Web guarantees immediate expiry filtering. No new Support operator endpoints are introduced.

Terraform grants `roles/datastore.user` to hosted and local Admin identities. This authorizes database-wide writes, while application mutation entrypoints restrict writes to `information`. Existing viewer grants remain to avoid deleting protected IAM resources. Apply and verify IAM separately for each explicitly selected environment; emulator success does not verify cloud permissions.
