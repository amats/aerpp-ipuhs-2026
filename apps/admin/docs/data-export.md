# Research and participant access exports

`/research` downloads retained source records for offline verification and analysis. Admin's on-screen counts are temporary, simplified operational displays and do not aim to provide accurate research totals. Accurate aggregation is performed from these exports after selecting the appropriate records according to the study's criteria. Admin performs no statistical analysis or qualitative coding.

Each ZIP button shows request progress and blocks repeat clicks while its request is pending. **待機を中止** aborts the browser's wait, returns focus to the enabled save button and allows an explicit retry. Read, network or unexpected-response failures keep the operator on `/research`, display a fixed error without server-response details, and allow retry through the same button. Only a successful ZIP response with the expected download filename starts a browser download; the success message reports that download started, not that it was saved to disk. Cancelling the wait or leaving the page suppresses late downloads and feedback from that request, including during response-body retrieval. Browser cancellation does not guarantee cancellation of server-side processing already in progress; a retry creates its own fresh snapshot after capacity is available. One export per process is admitted; overlapping requests receive 429 with Retry-After: 15. An uncancellable SDK snapshot retains that slot until its original promise settles, even after the HTTP wait is cancelled or expires. Research and access requests remain independent. There is no automatic retry or additional browser timeout.

## Complete source export

The authenticated `/api/research/export` uses one fresh read-only Firestore transaction per download, fetching at most 32 documents per page sequentially within that transaction. Research records from closed withdrawal periods are excluded at acceptance, including records still awaiting physical cleanup. The original consent boundary determines exclusion; renewed consent never reopens a withdrawn period. Unresolvable withdrawal ownership or period linkage aborts the research export. All other retained records across servers, dates and purposes (research/test/unclassified) remain available without submission or questionnaire-version filters. Unknown answers, missing measurements and old versions remain unchanged for offline review. Access exports retain operational history across withdrawal periods. These are selected-field exports, not credential-bearing database backups.

Numeric measurements in ZIP source JSON retain the Firestore value type and representation: numbers remain numbers, numeric strings remain strings (including whitespace/leading zeros), and null, missing or unsupported values remain distinguishable. Monitoring may convert finite decimal numeric strings for calculations, but exports never use that normalized projection or write conversions back to Firestore. CSV renders textual cells and cannot alone preserve JSON value types; use source JSON for exact value-type checks. Timestamp serialization, field selection and privacy exclusions below still apply.

Physically deleted research cannot be reconstructed. Withdrawal retains operation start/end observations, server receipt times, outcomes, presentation/submission/loss facts, original and recovered submitting ownership, deletion jobs, authentication history and consent/recovery decisions separately from research payloads. Access records exclude measured durations, model/count fields, answers and research retry copies. Timestamp differences may imply an approximate interval; never use them to restore withdrawn or missing research durations. Research exports preserve valid retained `durationMs` and `processingDurationSeconds` values in their original units. Previously downloaded research copies require separate withdrawal reconciliation.

Access histories retain `hasCompletedAnalysis` captured at withdrawal: true means completed-analysis evidence existed, false means no attempts existed or all attempts had confirmed failure/cancellation, and missing/null means unconfirmed. This is historical evidence, not the current period's completion status. Recovery cannot revive physically deleted answers or measurements; an original-initial-questionnaire target requires its retained research record.

## Files and formats

| Query | Contents |
| --- | --- |
| `dataset=research&format=bundle` | Research ZIP: `source.json`, `analysis-questionnaires.csv`, `attempts.csv`, `questionnaires.csv`, canonical `questionnaires/jcs-v1/sha256/<digest>.json` files, README |
| `dataset=access&format=bundle` | Access ZIP: `source.json`, `participation-events.csv`, `participation-states.csv`, `email-confirmations.csv`, `analysis-access.csv`, `survey-access.csv`, `access-events.csv`, `withdrawal-jobs.csv`, README |
| `dataset=research&format=json` or `dataset=access&format=json` | Corresponding JSON source and manifest |

Individual CSV queries use the JSON dataset key: `analysisQuestionnaires`, `attempts` for research; `participationEvents`, `participationStates`, `emailConfirmations`, `analysisAccess`, `surveyAccess`, `accessEvents` or `withdrawalJobs` for access. For example, `dataset=access&format=participationEvents` downloads `participation-events.csv`. Defaults are research/JSON; unsupported combinations return 400. Research uses schema version 6 and access uses version 8. These schemas use the current collection and measurement names; offline importers must use the matching format. An unavailable email remains `復号できません`.

Research and access are downloaded separately. Access ZIP and standalone JSON/CSV may contain decrypted personal information and are exempt from file encryption; they are generated in memory without persisting plaintext on the server. Each request has its own `exportId` and `snapshotAt` and may observe different data; join records using their stored linkage IDs, not export IDs. Manifests report read/exported row counts and research exclusions by closed participation period. Failure of any read or archive creation returns an error instead of a successful partial download. Files are generated in memory without server persistence; responses are private and noncached.

JSON preserves absent keys, empty strings, null, invalid values and nested receipts. Firestore timestamps retain seconds/nanoseconds, and nonfinite numbers have `firestoreNumber` tags. CSV uses UTF-8 BOM, quoted cells and formula protection; JSON is authoritative for distinctions CSV cannot represent. Missing fields produce empty CSV cells, including custom field names such as `toString`.

Record CSVs reserve `sourceDocumentId` for the Firestore document ID. A stored field with that name becomes `data.sourceDocumentId`; any stored key already beginning with `data.` gains one more `data.` prefix to avoid collisions. Other stored column names remain unchanged. A derived `<column>Utc` column is added for valid Firestore timestamps only when no stored field maps to that column anywhere in the same CSV. For example, a custom answer named `submittedAtUtc` retains its value and prevents generated UTC values from being mixed into that answer column on other rows. Original keys and timestamps remain in JSON. Each archive's README and manifest `csvColumns` describe this convention.

Each snapshot admits at most 20,000 selected documents and 16 MiB of serialized source data across its collections; questionnaire originals have a separate 16 MiB aggregate limit. Generated files total at most 32 MiB, and each CSV allows at most 1,000,000 data cells. Pretty-print expansion is checked before allocating JSON. These are conservative per-process resource bounds, not record filters: exceeding them fails the complete request without a download. Standalone JSON/CSV generates only the selected file, so a wide CSV does not prevent a complete JSON export. Larger installations need a separately designed export path; no durable export queue or server-side plaintext files are created.

## Research fields

Each completed analysis records required `analysisWorkspaceVersion`, the workspace version captured by Web when that analysis starts. Research JSON, the ZIP's `source.json` and `analysis-questionnaires.csv` preserve this field and its metadata receipt alongside the answers linked by `analysisId`. Later submissions, retries and administrator recovery do not replace it with the current Web, Support or Admin version. Access exports do not include it. Resolve the recorded version to the fixed GitHub source release described in [research provenance](../../../docs/research-release.md#release-provenance); the export does not collect model configuration details or a separate questionnaire-screen version.

Free text is assumed not to contain personal information and is preserved without mandatory screening. Surveys retain answers (including free text), recorded backgrounds/context/purpose, model name, document/result character counts and processing time. Attempts retain start/end observations, per-document character counts, outcomes and duration. IDs (`pseudonym`, `consentId`, `analysisId`, `clientId`, `serverId`) retain offline linkage. Research ZIPs include every referenced canonical definition. Standalone JSON/answer CSV exports contain references and source data only; the questionnaire dictionary is ZIP-only. Stored `surveyVersion` values are retained without validation, rewriting or filtering; absent historical values remain absent. This differs from the required `survey_version` field in the accompanying questionnaire definitions.

The questionnaire dictionary (`questionnaires.csv`) includes `construct` and `reverse` alongside each item's ID, wording and requirement. `reverse` preserves explicit true/false values; it is blank when the definition has no flag, including non-Likert items. Likert `options` lists the actual labels submitted by Web, while `valueLabels` maps score keys to those labels. ZIP source JSON preserves the full definitions. Exported answers remain unchanged; scoring and reverse scoring belong to offline analysis.

Research ZIP creation retrieves definitions from the selected project's Cloud Storage archive, verifies canonical JSON bytes and the full `jcs-v1:sha256` ID, and includes each definition once. Reads run in parallel with at most four in flight. Each Cloud Storage request has a 60-second timeout; every download format shares a 90-second read deadline starting before the Firestore snapshot read, and research ZIP questionnaire retrieval uses its remaining time. If that deadline expires while Firestore is pending, the request returns 503 without starting questionnaire retrieval or ZIP generation. Already-started Firestore SDK reads may finish afterward; late results and failures are ignored. A deadline, read failure or client cancellation aborts outstanding questionnaire requests and leaves queued definitions unread. The application allows 110 seconds for the complete export and checks cancellation after bounded generation phases and between ZIP checksum chunks. Hosted Admin requests allow 120 seconds, reserving time for authentication and delivery. Synchronous bounded phases are not forcibly interrupted by JavaScript timers. Admin images contain no questionnaire JSON. Missing/corrupt referenced definitions or read failures abort the entire ZIP, without current-version fallback or successful partial output. Submitted responses without a reference abort the ZIP; unsubmitted completion metadata does not require a definition. Normal monitoring, standalone JSON/answer CSV and access downloads never read Cloud Storage. Explicit document verification/reissue reads the separate document archive. Byte-exact editable originals are not retained. See [identity and registration](../../../docs/examples.md#questionnaire-definitions).

New answers are nested under `answers`, including null for untouched optional items, and reference `questionnaire.kind` and `questionnaire.definitionId`. CSV represents nested objects as JSON cells; source JSON remains authoritative. Join dictionary rows by `definitionId` and `itemId`, never by a human version name alone. Stored historical flat answers and descriptive `surveyVersion` values remain available unchanged in raw exports.

`processingDurationSeconds` is seconds and `durationMs` is milliseconds. Current `documentGraphemeCount`/`resultGraphemeCount` store grapheme counts, not model tokens. Missing terminal observations do not mean failure. Missing `submittedAt` does not mean a submitted questionnaire. Count people, attempts and answers separately offline; no derived cohort or score is exported.

Structured contact and credential field names are removed recursively from research records. Documents and AI-result bodies are not collected. Free-text answers are preserved verbatim; review them offline for inadvertently entered personal information before sharing.

The reserved contact/credential names come from `PRIVATE_PARTICIPANT_FIELD_NAMES` in the shared [participant contract](../../../packages/contracts/src/request-schemas.ts). Web rejects these names as questionnaire answer IDs when loading definitions, preventing accepted answers from silently disappearing during export. See the [questionnaire ID requirements](../../../docs/examples.md#questionnaire-definitions). Existing private-field filtering remains in effect for historical records.

The research files retain stable linkage identifiers and can be joined to the separately held access files; removing email fields does not make them anonymous. Keep both downloads under the study's access and retention policy, and record their separate snapshot times when reconciling a changing dataset.

## Participation and activity fields

The access export contains projected consent/withdrawal history, participation state and stored authentication status/timestamps, plus analysis start/end and survey creation/submission metadata. Consent and pending authentication records include decrypted email addresses as `email`; newly completed authentication rows remove the duplicate ciphertext and source exports preserve its absence. Neither `encryptedEmail` nor encryption keys are exported. Missing email fields remain absent, and null/empty values remain distinct in JSON. A malformed value, wrong key, tampered seal or failed email decoding sets that row's `email` to `復号できません` in JSON and CSV. The row remains included in the export and its counts, and other addresses are decrypted normally. The marker is a status message, not a contact address; no original encrypted value or error detail is exported. Store these files separately from research data. No answer body, authentication token, verifier, nonce, request hash or credential is exported. Access is subject to the existing Admin allowlist; keep its authorized accounts aligned with the study's responsible-researcher restriction.

Each consent/withdrawal row includes its retained `documentSet` reference and `did`, reconstructed from that record's own `consentConfirmedAt` or `withdrawalAcceptedAt`. Web exact-record copies and Admin exports agree; later confirmations never replace an earlier copy's date or DID. A withdrawal must link to its retained consent by PID and consent ID.

The date uses the Japan calendar as `YYYY年M月D日`. Web and Admin use the [shared v2 HMAC-SHA-256 contract](../../../docs/identifiers.md), binding email, purpose, Japan date and document-set SHA-256. Same-day confirmations for the same email, purpose and set share a DID. This derived value proves neither issuance nor delivery. Missing/unreadable contact, date, document reference or withdrawal linkage produces JSON `null` / an empty CSV cell without substituting another date or current set. Reproduction requires the original identifier key and derivation contract. See [document history, verification and reissue](../../../docs/document-sets.md#copies-verification-and-reissue).

Invalid calendar dates, ISO strings without a timezone and out-of-range Firestore timestamp components also produce null DIDs. Raw values remain in the export; invalid timestamp objects do not receive a derived `*Utc` CSV column. Valid Firestore timestamps use the same millisecond rounding as Support's timestamp-to-ISO conversion, including rounding across midnight in Japan, so reconstructed DIDs agree with the dates Web receives. JSON retains the original nanoseconds.

Admin receives the selected profile's existing `SESSION_SEAL_PASSWORD` and `IDENTIFIER_HASH_SECRET` from the same `secret.json` keys as Web. Keep both keys stable; replacements cannot decrypt historical records or reproduce previous document IDs. Hosted delivery uploads them through the normal private secret preparation and immutable-version workflow, never ordinary Terraform runtime values. Apply the Admin secret container/IAM foundation, prepare the updated Admin image and secret versions, then apply/promote the revision through the existing deployment procedure. Local checks do not deploy these changes. Export-only decryption verifies integrity while disregarding the seal expiry so retained contacts remain available after reception closes; it does not alter participant/session authorization.

Authentication `createdAt` records issuance and `updatedAt` records the saved status update; consent uses `consentConfirmedAt`, and withdrawal uses `withdrawalAcceptedAt`. Confirmed consents also retain the first `consentRequestedAt`, unchanged on resend. New authentication requests have durable typed participation history even if an unused challenge expires; withdrawal archives safe challenge metadata before retiring credentials. These records establish accepted requests, not mail delivery or the exact consent-button click. Missing historical observations remain missing.

`analysisRuns` supplies operation summaries after research deletion. `accessEvents` supplies first accepted transition receipts; exact retries retain the original timestamp. `withdrawalJobs` supplies the accepted boundary, committed questionnaire deletion count and cleanup status/completion time, matching the state cache. Access exports read operational observations from `analysisRuns` without falling back to research records. No page-view/IP/Cloud Logging export is implied. Late terminal observations for a historical run can update its operational receipt after owner validation, without restoring research payloads, releasing a newer claim or changing current permission.

Web, Support and Admin must use the same event-timestamp schema. Deploy matching versions before accepting new participation.

## Runtime and checks

Admin runs on Node.js. ZIP tests use the independent `unzip` command; install it alongside workspace development tools.

Run the [Admin verification and browser checks](../CONTRIBUTING.md#development), workspace build and image checks. Tests cover all-row retention beyond former limits, contact/answer separation, authentication, independent download provenance, expired-email decryption, unreadable-email markers and null DIDs alongside valid rows in JSON/CSV/ZIP, CSV column collisions and missing cells, tamper/wrong-key rejection by the decoder, ZIP interoperability and failed reads. Synthetic checks do not establish actual cloud record counts or deployed access.

The [cross-app PDF/export contract test](../../web/tests/participant-document-export.test.ts) runs with Web tests. It compares exact-record Web PDF generation with each consent/withdrawal export DID, including multiple devices, same-day confirmations, Japan-time date boundaries and participation periods separated by withdrawal.

## Synthetic sample

Run `pnpm --filter @aerpp/admin run research:sample` to generate `generated/reports/export-sample/research-source-SAMPLE.zip` and `access-source-SAMPLE.zip` as separate archives. The script uses public questionnaire definitions and fictional records with decrypted `example.invalid` email addresses, without cloud access. Generated files are not editable sources. Invalid, missing and unsupported observations intentionally exercise offline import checks.

`SAMPLE-P008` has an unreadable email in its consent, withdrawal and authentication records. All three rows remain included, with `email` set to `復号できません`; consent/withdrawal `did` is null in JSON and blank in CSV. Other participants demonstrate successful decryption. `SAMPLE-P007`'s withdrawal has no email field, preserving the distinction between missing and unreadable values. The generated `SAMPLE-GUIDE.md` identifies these cases for offline importer checks.

Shared persistence and field projection are documented in the [Firestore package](../../../packages/firestore/README.md#research-snapshots-and-values). The operational study plan is supplied privately at `apps/web/assets/plan.pdf`; its public template lives in `apps/web/assets-public/plan.pdf`; analysis inputs and results remain local.


Recovery audit projection includes PID, selected destination/kind, original analysis ID/source owner when applicable, expected generation, reason, pseudonymous actor ID, authorization/consumption/supersession timestamps, recovery ID and consumed consent ID. Participant state also projects study generation/eligibility, protected initial attempt, initial acceptance and recovery authorization. These are source metadata; no plaintext email, document or result is introduced by the recovery projection. Consent/withdrawal activity continues to use its own event timestamps rather than treating recovery as consent.

Admin **参加者** recovery uses review then confirmation, rejecting stale forms. Initial-survey targets must have a retained completed initial attempt and completion receipt with no accepted answer. The original source owner remains in research metadata; its new submission linkage is `recoverySubmission`.
