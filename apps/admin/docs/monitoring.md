# Admin operational monitoring

This guide owns record meanings, counts, filters and log display. Read [cross-application record definitions](../../../docs/architecture.md#analysis-and-questionnaire-records) and [source exports](data-export.md) alongside it. Source paths are relative to `apps/admin`.

## Survey aggregation

The counts below provide a quick operational overview. They are not intended to guarantee accurate or final research totals. Use [data exports](data-export.md) to select the appropriate records and perform accurate aggregation separately.

Operational participant and survey timestamps are labeled in Japan time. Tables show the displayed count and total count; their latest-200-record limit does not limit the summary metrics. See [notice editing](information.md#information-management) for focus, draft and concurrent-update behavior.

When no analysis attempts match the current scope, the survey page shows an explicit empty message. Populated attempt tables keep their headings readable and scroll horizontally within the card on narrow screens; keyboard users can focus the table region and scroll with the arrow keys.

Admin does not bundle questionnaire definitions. Normal monitoring reads Firestore only, even when Cloud Storage is unavailable. Definition retrieval is restricted to research ZIP creation. See [questionnaire identity and delivery](../../../docs/examples.md#questionnaire-definitions).

Survey documents first record completed-analysis metadata; answer submission adds `submittedAt`. Recorded analysis completions and submitted responses are counted separately. Respondent counts, answer activity and item summaries require a valid submission timestamp. Activity is ordered and dated by submission, and summaries show counts only. Processing time and document count remain in stored records and exports; the time histogram also groups completed analyses by duration. Record lists retain unanswered analyses and label them as unsubmitted. The `BG1` and `BG2` columns identify stored answer IDs without assigning fixed question meanings.

Records normalize valid timestamps and finite numeric metadata and read the nested `answers` map and `questionnaire.definitionId`. Initial and follow-up item counts use the recorded `analysisAttempts.questionnaireKind`, joined by analysis document ID and matching `clientId`, `pseudonym`, `serverId` and `consentId`. Missing or unrelated attempts leave the kind unknown: the records still count toward submitted-response and respondent totals, but cannot be assigned to an initial/follow-up item group. Stored `surveyVersion` values do not determine the group, authorize a response or filter records; the required definition field `survey_version` is a separate input requirement.

Item summaries sort by definition ID and question ID and count nonblank stored string answers for each recorded answer ID, separately for each definition, excluding section headings. They do not convert labels to scores, impose a numeric range, apply reverse scoring or calculate means. Unknown nonblank labels still count as recorded answers; missing, blank and non-string values do not. Null entries preserve zero-response items without fetching definitions. Stored values and questionnaire JSON remain unchanged, and scoring definitions are retained in exports for offline analysis. Dashboard and survey summaries contain counts only, without averages for scores, processing time or document count.

Initial use means completing both analysis and the initial questionnaire; unanswered attempts, including force-reset recovery, do not complete it. Participants are distinguished by the stable pseudonym derived from the trimmed, lowercased email address, rather than browser/client IDs. Firestore study state protects initial presentation through acceptance; researcher authorization can explicitly select initial/follow-up eligibility for a new consent without changing historical facts; analysis attempts and research utilization metrics remain separate. Local mocked Firestore tests do not verify deployed data or access permissions.

The survey page also reads `analysisAttempts` separately from questionnaire responses. It shows observed terminal outcomes and **終了未確認** for starts without terminal observations (including still-running work), per-document body grapheme counts, duration and the consent record ID. An attempt marked completed means output and a completion receipt were prepared; it does not establish browser delivery, result persistence or questionnaire submission. Attempt and survey record lists display at most 200 records each, while their counts use all loaded records matching the server filter.

The dashboard has a separate **解析の実行状況** card showing analysis starts and completed, failed, cancelled and unconfirmed outcomes. It shares the survey page's attempt aggregation, uses all retained attempts matching the configured server and selected data purpose, and refreshes on load/reload. These counts are independent of the one-day attention-log window and questionnaire submissions; completed-analysis metadata never creates inferred attempts. The detail link retains data purpose and opens the survey page.

Participant status uses the latest loaded consent/withdrawal event across all servers and data purposes for participants selected by the configured server and purpose filters. History lists, activity and record counts remain filtered; a withdrawal recorded under another server or purpose therefore changes current status on the next load without broadening the monitored participant set. This also handles unclassified history and classification changes between consent events.

Renewed participation retains the email-derived pseudonym and references a new confirmed consent; withdrawal removes its surveys and attempts but preserves consent/withdrawal history. Existing surveys have no inferred attempt records. Current retained data therefore does not establish all-time execution or participation totals. See the [cross-application record definitions](../../../docs/architecture.md#analysis-and-questionnaire-records).

### Analysis time distribution

The survey page plots retained `analysisQuestionnaires.processingDurationSeconds` values, including analyses whose questionnaires have not been submitted. It uses every record matching the configured server and selected data purpose before the 200-row list limit. The horizontal axis is seconds and the vertical axis is the number of completed-analysis records; a collapsible table provides each interval's count. No average or score is calculated. Like the other operational summaries, this is a temporary, simplified display; accurate aggregation belongs in offline work after source export and record selection.

Web records whole seconds from analysis admission through output completion, including preparation. This is distinct from `analysisAttempts.durationMs`; missing survey times are never filled from attempt durations. For display and interval calculations, the record reader accepts finite numbers and decimal numeric strings (including surrounding whitespace, signs, fractions and exponent notation). It rejects empty strings, booleans, hexadecimal notation and nonfinite conversions. These conversions affect only the in-memory monitoring projection; research ZIP source values retain their stored number/string representation. Zero and fractional values are included; missing, blank, nonnumeric, nonfinite and negative times count as **時間不明** and do not affect interval selection. Changing filters or reloading recomputes the distribution from the current retained data.

Intervals use the [Freedman–Diaconis rule](https://numpy.org/doc/stable/reference/generated/numpy.histogram_bin_edges.html): estimated width `h = 2 × IQR / n^(1/3)`, with linearly interpolated quartiles at positions `(n - 1) × 0.25` and `(n - 1) × 0.75` in the sorted valid values. The number of bins is `ceil((max - min) / h)`, and the actual equal width spans the full observed minimum-to-maximum range. Intervals include their lower edge and exclude their upper edge, except the final interval also includes the maximum.

If IQR is zero, the FD calculation is not finite, or FD would require more than 200 bins, use Sturges' rule `ceil(log2(n) + 1)` instead. This display safeguard avoids excessive bars without discarding outliers or adding an open-ended last bin; the caption identifies the method used. Identical times use one bin labeled with that value, and no valid times produces an empty-state message. Displayed interval labels are rounded for readability; assignment uses the unrounded edges.

## Research and test data

The dashboard displays environment-wide notices without dismissal controls, independently of the fixed server scope and data-purpose filter. Notice failures remain local to the notice panel. Like Web, notices remain visible until deletion, including asynchronous TTL deletion. Dashboard attention items use a fixed one-day window and the same event classification as the operational status page. Its detail link retains data purpose. The operational status page has a shared 1/7/30-day window for usage and logs.

The dashboard includes Google Cloud Console shortcuts for project overview, logs, Error Reporting, monitoring dashboards, alerting, Cloud Run, Firestore, Cloud Scheduler and billing. Each link uses the current Admin project from its private environment, opens in a new tab, and requires the operator's own Console permissions. Billing opens the project's linked billing account entry point. Links are unavailable without a configured test/production project; no cloud requests or permission changes are performed to render them.

The dashboard also previews the four most recent participant/survey updates using the same activity semantics as `/updates`; its detail link retains the selected data purpose.

Operational dashboard, participant, survey and activity views default to `dataPurpose=research`. The data-purpose selector offers research, test, unclassified and all records; selection applies before aggregation and display limits and is retained in navigation. Missing/invalid stored purposes appear as unclassified. The server scope is fixed by the environment. Logs, maintenance results and information messages are environment-wide operational data and are not classified by participant purpose. The operational status selector applies only to its usage panel.

If an operational data read fails, these views retain their navigation and current filter and display a retry button instead of zero counts or empty records. Retrying refreshes the current route. Diagnostics contain only the operation and an allowlisted numeric status; SDK messages and participant data are excluded. Unexpected page failures offer retry and a dashboard link. Recent-activity cards wrap full participant identifiers on narrow screens; record tables retain their own horizontal scrolling.

Research exports exclude closed withdrawal periods in their consistent snapshot, including pending cleanup; renewed participation is evaluated using the original consent boundary. Other retained research records remain across purposes, servers and dates. Access exports include retained history across withdrawal and may contain decrypted email addresses and reconstructed consent/withdrawal PDF `did` values in ZIP or standalone JSON/CSV. Unreadable emails remain `復号できません` with null DIDs. Manifests report read/exported counts and withdrawal exclusions. Accurate study eligibility and aggregation still belong offline. See [data export](data-export.md).

Configure dedicated researcher mailboxes before use in the [private profile](../../../docs/configuration.md#test-participants-in-production). Existing unclassified records are retained for operational review, never automatically promoted to research or deleted. Reviewing historical data does not authorize bulk reclassification. The offline synthetic sample remains labelled SAMPLE and performs no Firestore writes.

Consent history ordering, status summaries and displayed event times use `consentConfirmedAt` or `withdrawalAcceptedAt`; they never substitute request time or `createdAt`. The participant table separates `同意申請日時` from `同意確認・撤回受付日時`. Request time is not evidence of confirmed consent; withdrawal rows have no consent-request time.

Participant, survey and analysis record dates accept valid `Date` values, finite epoch milliseconds, ISO timestamps with an explicit timezone, or valid Firestore seconds/nanoseconds. Calendar overflow, timezone-free strings and malformed timestamp parts remain unknown; invalid `submittedAt` values do not count as responses. Firestore timestamp conversion follows Support's millisecond rounding so operational views and access-export DIDs use the dates delivered to Web. Raw exports preserve the stored values for offline review.

## Cloud Logging

Cloud Logging lookup failures display a fixed retry message. Admin's structured diagnostic boundary records the operation and a bounded numeric SDK status only; it excludes SDK messages, details, stacks and credential/project identities, including initialization and project-resolution failures. Only the safe operational projection is displayed to authorized administrators. NextAuth diagnostics use fixed authentication error/warning classifications instead of its default raw OAuth error and metadata output; debug metadata is discarded. Successful recovery grants have durable Firestore receipts; duplicate application success logs are omitted. Scheduled maintenance INFO results remain because the latest-maintenance display depends on them.

The operational status page replaces raw log bodies with catalogued Japanese event descriptions. The adapter drops messages, URLs, identifiers, unknown event/operation/code strings and nested payloads; only reviewed classifications, normalized timestamps/severity, bounded HTTP status and nonnegative aggregate maintenance counts reach the display. Application logs use Cloud Logging severity; proxy string levels retain their native mapping. Unknown/platform records use a fixed service-specific description. Expected rejection, cancellation, admission closure and cleanup-pending observations are distinct from system failures; transport retries are counted separately and do not imply either final success or failure. Final dependency 4xx responses, except rate limiting, are shown as rejections. Unexplained warnings and partial reads require attention; a rejection label does not suppress an observed 5xx or error-level failure.

Cloud Run queries and service classification use the Terraform revision label `aerpp-component` (`support` or `admin`), independently of deployed service names. List, latest-maintenance and Console investigation queries share the same component scopes. Support and Admin serving revisions must carry these labels; older unlabeled revision logs are outside this scope.

Queries use a single fixed start/end window and include application-owned Web/proxy, Support/Admin and maintenance Scheduler resources, including proxy 5xx status payloads even without error-level severity, while excluding successful unclassified request traffic and unrelated project logs. General events are read in at most five 200-entry pages with a per-request deadline; a remaining page token marks the result incomplete. Attention groups show log occurrence counts, first/last observation, and at most 20 groups (four on the dashboard). These are neither operation counts nor unresolved-incident counts. The event list shows at most 100 retrieved records. Incomplete retrieval is explicitly labelled; a failed read is never displayed as zero errors. Filtered Console links use the current private project and require the operator's own Console access.

Attention items are review candidates, not confirmed outstanding tasks. Each type includes a short reason explaining the possible operational impact and what to confirm. HTTP status labels distinguish otherwise unclassified request records, including authentication/permission rejection, missing targets, conflicts, rate limiting and server failures. The selection and grouping rules remain unchanged: Cloud Run request warnings for ordinary 4xx responses stay visible because they can also indicate production access problems. Expected test traffic does not establish a production incident; confirm recurrence, user impact and the current state before taking action. Historical maintenance failures likewise require checking the latest job result.

Each group displays its HTTP status when available. Its investigation link narrows the selected time window to the service, catalogued event/operation/code and that status, using the same status-field precedence as the display projection. The link excludes ordinary unclassified success/startup records and escapes query parentheses so they cannot be interpreted as Console route syntax. An expandable query provides the same search conditions and a compact clipboard-copy button for pasting into Logs Explorer if Console navigation drops the URL state. Copy success or failure is displayed locally; if clipboard access fails, the query remains available for manual selection and copying. No raw log text or private participant fields are added to these descriptions or queries. Generating and testing a URL does not verify authenticated Console navigation.

Each scheduled maintenance operation has an independent latest-result query within the selected period so busy event traffic cannot hide its result. Empty pages with continuation tokens are followed up to the same five-page cap; reaching the cap without a result is unavailable, not proof of absence. One failed operation lookup does not discard the other operation's observed result. Display completed, failed, outside-window skipped, unknown and unavailable states separately. An observed success is not current uptime or mail-delivery evidence. Cleanup counts belong to that one bounded sweep, not the full outstanding work list; successful sweeps with pending candidates show carried-over work. Missing results do not imply normal operation or an outage. Queries do not dispatch jobs, send mail or change monitoring infrastructure.

### Operational usage

Usage reads fresh Firestore records with the fixed server and selected purpose, independently of Cloud Logging. A failed usage read leaves logs and maintenance available and displays a retry instruction instead of zero counts. Count confirmed consent and accepted withdrawal by their event timestamps, analysis starts and current terminal/unconfirmed outcomes by `startedAtMs`, completed-analysis records by `createdAt`, and submitted responses by valid `submittedAt`. Do not infer attempt records from completion metadata. This usage view reads research records and can decrease after withdrawal; retained operational runs are available through recovery lookup/access export. Initial/final days include only observations inside the rolling window; day buckets use Japan time. Unknown consent/withdrawal, start or completion timestamps are excluded and reported separately across the selected retained scope. Outcome counts describe attempts started in the window; they are not terminal events observed during the window. Unconfirmed includes still-running attempts, and completion does not establish delivery, viewing or response submission.

Usage counts and zero-filled daily tables use all matching loaded records, independently of table display limits. They describe currently retained data and can decrease after withdrawal. Do not interpret them as all-time totals, final research results or a participation funnel. No means, model configuration changes or additional research measurements in operational logs are introduced. The existing survey histogram and participant/recovery pages remain the detail destinations. The `/updates` route is labelled **参加・回答履歴** to distinguish individual participant/response history from operational events.

Daily usage and event tables scroll within their cards and are keyboard-focusable. Period submission preserves data purpose; purpose selection and reload preserve the selected period.

Isolated emulator workflows use reserved `demo-` project IDs. Their dashboard and log page show that Cloud Logging is unavailable without initializing cloud credentials or making log requests.

Cloud Logging timestamps use Asia/Tokyo with an explicit Japanese-time label, independently of the server timezone.

## Read ownership and projections

`features/monitoring/participant-records.ts` owns fresh operational reads and aggregation. Its DTOs are in `participant-record-types.ts`. Monitoring projections exclude email ciphertext, token/credential fields and internal retry receipts. Dashboard and recent-activity reads also exclude answer bodies; the questionnaire page explicitly selects current questionnaire item fields. Independent dashboard reads run concurrently, while the full participation history remains available to determine the latest withdrawal across server/purpose filters. Attempt DTOs use `startedAt` for the stored `startedAtMs` observation. Full research/access exports retain their separate snapshot and field policies.

The questionnaire record table displays **解析時のバージョン** from stored `analysisWorkspaceVersion`, including completed analyses awaiting answers. This is the workspace version captured by Web for that analysis, independent of the running Admin version and questionnaire definition ID. It does not select a questionnaire kind, gate counts or alter research eligibility. Research source JSON and CSV retain the field; access exports exclude it with the other research metadata.


## Researcher recovery

The authenticated participant page starts with **PIDの記録を照会する**. Operators can enter a PID directly or select **メールアドレスからPIDを生成して照会**. Email-derived PIDs follow the [shared versioned HMAC identifier rules](../../../docs/identifiers.md). Email input is used only for this authenticated request, never stored or logged, and is not returned in the result. The selected method and entered value remain in the current form after lookup so repeat requests use the same identity mode.

Before selecting a destination, operators can review the current environment-wide participant state, consent/withdrawal/recovery and accepted access events and retained operational runs with analysis outcomes and completion/presentation/submission metadata in one read-only Firestore snapshot. Recovery history reads `analysisRuns` directly; it does not reconstruct missing runs from research records. History uses the configured server scope and includes research, test and unclassified records regardless of the page's purpose filter; all retained matching records are listed with counts. Contact ciphertext, authentication credentials, answers and analysis content are excluded. Missing records remain missing, and presentation permission is not evidence that the participant viewed a result. Editing the lookup input hides the old target and decision form until a new lookup succeeds; a missing participant state provides no decision form. Repeat lookup to refresh the snapshot after a decision.

After reviewing the records and the participant's report, select **復旧先**, the target analysis ID when needed and a required reason. **対象を確認する** reviews the proposed decision; **確認して復旧を許可する** rechecks exact record versions before saving. It retains prior study facts and stores a one-time grant plus `recovery_authorized` audit in existing participation history, with pseudonymous actor ID, authorization time and consumption time/consent. New ordinary consent/email confirmation consumes it; no email bypass or public reset is added. A later decision replaces the entire pending grant, never inherits consumed fields. Withdrawn participants require confirmed cleanup first.

If confirmation loses its response or encounters a transient commit error, retain the reviewed recovery ID and inputs and retry the same confirmation. The server rechecks authorization and either recognizes the matching durable receipt or validates current versions before writing. Never generate a replacement grant merely to resolve a lost acknowledgement. A changed/unavailable target requires another review. Page-refresh failure after a confirmed commit does not reclassify the grant as failed.

The same page lists recent recovery audits separately from consent/withdrawal status, including reason, actor and consumption. Current participant status derives only from consent/withdrawal events. Filters remain server/purpose scoped and source exports preserve audit fields without analysis content. Local/emulator checks do not establish real OAuth/IAM acceptance.

### PDF document verification

The authenticated participant page includes **PDFのDID照合**. Enter the PDF's
email, Japan calendar date, consent/withdrawal purpose and DID. Server-side HMAC
comparison checks that binding; email and secret are not persisted or logged.
The returned PID can be used in the separate history lookup. A match does not
assert that an acceptance record exists, that a download occurred, or that the
PDF body is unchanged. Check the retained consent/withdrawal date and purpose in
history separately. The body is fixed and published at study start; it is outside
the DID integrity boundary. The selected document type and entered binding remain
visible after verification, including on a mismatch; repeated verification uses
those same values. Edited inputs discard the prior result.

## Document verification and reissue

The participant page checks printed v2 DID inputs, archived originals and actual receipt history separately. PID lookup exposes exact document records for authenticated reissue within the configured server scope. Reissue uses the recorded date/set and writes a pseudonymous durable access receipt before returning a PDF; it never restores participation or deleted research. A rendering/delivery failure does not affect participation; retry or use the participant application's download path when available. Once rendering succeeds, a lost audit-update acknowledgement must not overwrite a possibly committed `generated` outcome with `failed`; generated still does not prove delivery. The download belongs to the participant and record selected when reissue is requested. Selecting another participant while generation is pending does not cancel or retarget that download. See [document sets](../../../docs/document-sets.md#copies-verification-and-reissue).
