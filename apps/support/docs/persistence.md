# Participation persistence

[Request schemas](../../../packages/contracts/src/request-schemas.ts), [public contracts](../../../packages/contracts/src/participant-api.ts) and [OpenAPI](../../../packages/contracts/src/openapi.yaml) own payloads. The [shared Firestore package](../../../packages/firestore/README.md) owns participant/information references, queries and research snapshot projections. The Support service owns write transactions and participation policy; [deployment](../../../docs/deployment.md) owns delivery and [local verification](../README.md#local-verification) owns test execution.

## Ownership and transactions

Read participation state and the relevant email-confirmation/participation-event records in the same transaction as writes. Finish every read before any write. Assume transaction callbacks repeat; never send mail, HTTP responses or logs inside them. Accepted operation receipts are written in the owning transaction; exact retries preserve the receipt and return success without another acceptance event. Duplicate success logs are omitted when durable receipt coverage exists. Operational logs are best-effort diagnostics, not durable delivery acknowledgements or an exactly-once audit. The authenticated caller's serverId restriction supplements participant ownership checks. Unknown fields, invalid Unicode, reserved keys and Firestore depth/size violations are rejected before persistence.

## Authentication

Sending requires a caller-prepared consentId, fixed deadline, encrypted email, owner and preceding-withdrawal boundary. Exact retries reuse the original pending identity and deadline. Reject changed content and stale history on every transaction attempt. Sending never confirms consent. HTTP mail work has a 50-second budget measured before caller rate limiting. Check it before starting or retrying a transaction and after its awaited commit; exhaustion retains any committed pending identity and recipient cooldown. OAuth and Gmail each allow 15 seconds, and delivery starts only when the remaining budget can cover its full dependency wait plus response headroom. No deadline race detaches database writes, and no automatic mail resend is introduced. Mail attempts share a durable recipient cooldown of 60 seconds and a maximum of five attempts per fixed hourly window, including retries, new consent IDs and different callers. Failed or ambiguous delivery still consumes the attempt; completed-consent retries send no mail. Keep the confirmation token distinct from consentId. Store only its verifier and a non-secret nonce, never plaintext tokens or emails; derive retry tokens with a server-side key that remains stable across exact retries.

GET /email/confirm displays a page without authentication side effects. The browser removes the URL fragment and submits the token with a same-origin JSON POST only after explicit user action. Consume it transactionally once. Bind pending records to the issuing credential ID; preserve the caller-prepared pending deadline (at most 65 minutes from issuance), independently of Web reception closure. Backend stop and caller revocation still fence confirmation. Confirmation rechecks the current credential/admission policy before creating consent. Completed proof has no application expiration and removes the pending TTL, duplicate email ciphertext and nonce. Reuse never changes confirmed consent or its first timestamps. Unbound pending records require fresh consent and mail issuance; do not infer their issuing credential. Stored pending expiration governs link use independently of asynchronous TTL cleanup.

Verification requires retained completed authentication and current confirmed version-2 consent. Missing authentication proof is rejected and is never reconstructed from other records.

The anonymous JSON confirmation route has a fixed-memory [process-local limiter](../src/confirmation-rate-limit.ts) before any Firestore operation: burst 60, refill 60 requests per minute and at most 20 in-flight confirmations. This allows ten simultaneous participants with retry headroom. Invalid links consume the same aggregate allowance; changing consent IDs, tokens or source addresses cannot create additional buckets. A permit remains held until the database promise settles, including SDK transaction retries and client disconnects. Database errors release the permit without changing token, consent or replay semantics.

Excess requests return HTTP 429 with `RATE_LIMITED` and `Retry-After`, without database access. The confirmation page disables its button until the indicated delay has elapsed, then permits a manual retry of the same link; it does not send automatic requests. A new link cancels the old wait. Each Support app instance has an independent limiter, with no participant-key cache or cloud rate-limit writes. Process restart or another replica has a fresh budget, so this is a per-process resource ceiling rather than a deployment-wide billing quota. Cloud capacity settings and monitoring remain separate controls.

## Consent and receipt timestamps

`emailConfirmations.createdAt` records the server's first accepted mail-issuance request, before mail delivery, and is preserved on resend. Successful email confirmation copies that original Firestore timestamp into `participationEvents.consentRequestedAt` in the same transaction that creates the confirmed consent. `participationEvents.consentConfirmedAt` records successful email confirmation; withdrawal events use `withdrawalAcceptedAt`, committed before deletion. Consent/withdrawal history uses these explicit event timestamps. Request time is audit metadata, never evidence of completed consent or permission to participate. An unconfirmed request cannot authorize participation or withdrawal. Unconsumed confirmation still enforces its fixed expiry; completed authentication and current confirmed consent provide authentication proof without an application deadline; withdrawal uses the retained current confirmed consent and its ownership/boundary checks independently of authentication-record retention.

The request timestamp survives authentication expiry/deletion because it is part of the retained confirmed-consent history. Mail failure or an ambiguous response does not change it on exact retry. Renewed consent has its own request timestamp and withdrawal linkage. Missing/invalid request timestamps remain absent; no request time is inferred from confirmation. Confirmation retries cannot rewrite either timestamp. Unconfirmed requests have a separate retained `authentication_requested` business record and pseudonymous access receipt, committed with the challenge. Neither is confirmed consent. Request history survives pending-link TTL; a deleted challenge cannot be reissued under the same consent ID.

These are server-received request, confirmation and acceptance times, not exact browser button-click or mail-delivery times. API history serializes available request timestamps as ISO date-time strings; Admin access exports preserve Firestore seconds/nanoseconds and include the explicit event timestamps. Consent PDFs use the latest `consentConfirmedAt` available at download time within the session's preceding-withdrawal boundary. Admin derives each exported consent `did` from that record's own confirmation date. Both use the same Japan-time date-string calculation, so same-day confirmations share a DID; no derived DID is written back to retained history. See [access-export fields](../../admin/docs/data-export.md#participation-and-activity-fields). Withdrawal PDFs use `withdrawalAcceptedAt` and remain acceptance receipts, not certificates of completed deletion.

## Renewed consent

Renewed consent waits for withdrawal cleanup. Every withdrawn participant requires an unused researcher grant in `participationStates.recoveryAuthorization`, including no-completion and failed-analysis cases. Both mail issuance and confirmation consumption enforce this requirement. Admin reviews and confirms PID, destination, optional original initial-analysis target, reason, pseudonymous actor and first timestamp with exact Firestore version checks in `participationEvents.recovery_authorized`. Confirmation consumes the grant once and sets `studyGeneration`; all consent-bound mutations compare it. Reopening the completed link reports `AUTHENTICATION_USED`. Pending links issued before a grant or from an old generation cannot consume it. Recovery never restores withdrawn research content.

## Participation and withdrawal

Withdrawal requires an owner-matched, email-confirmed version-2 consent record; pending authentication is never withdrawal authorization. Retained confirmed consent authorizes deletion retries after authentication cleanup or expiry. Withdrawal is pseudonym-wide, including other server/client instances. Commit withdrawn state before deletion and never roll it back after cleanup failure. All subsequent saves/authentication operations must observe the participant boundary transactionally. Ordinary email resend cannot undo withdrawal.

Before deletion, withdrawal captures `hasCompletedAnalysis` across the pseudonym: completed attempts or survey metadata mean true; confirmed failures/cancellations or no attempts mean false; a start without terminal outcome or invalid/absent evidence means null. State and withdrawal history retain this audit summary unchanged on retries. The HTTP 200 response includes it. No value authorizes ordinary renewed participation; every withdrawal requires administrator recovery.

Delete in bounded batches accounting for count and size. deletedCount is the cumulative committed survey deletion count; exclude authentication and analysis-attempt records and prevent double counting across overlapping requests. Every manual/scheduled cleanup attempt captures and checks one withdrawal-history ID, including completed-state shortcuts. Persist progress and a fair discovery cursor so a closed browser cannot strand cleanup. Keep participant/consent/withdrawal history; never put a TTL on participant state.

Consent, withdrawal, researcher recovery and authentication request/retirement records live in `participationEvents`. Contact ciphertext stays in these typed business records. `accessEvents` holds immutable content-free operation receipts, committed atomically with accepted commands; exact retries do not create another receipt. `analysisRuns` holds the transactional operational summary with original ownership, boundary/generation, start/end and server receipt times, outcome, completion/display/submission/loss observations and separately bound recovery submission ownership. These collections have no TTL. No measured duration, model/counts, answer, document/result or research retry body belongs in durable audit storage.

Ordinary cleanup deletes `analysisQuestionnaires`, `analysisAttempts` and active `emailConfirmations`. It preserves the allowlisted authentication projection as `authentication_retired` before removing obsolete proof. It preserves each research record's operational projection and per-payload deletion timestamp in `analysisRuns` in the same transaction as deletion. Existing run facts take precedence over a stale research copy, including a terminal receipt delivered during cleanup. Research deletion includes `_integrity` copies; deleted research is never reconstructed from audit times.

`withdrawalJobs/{withdrawalId}` records the exact closed consent boundary, acceptance, committed survey deletion count, progress and completion. `participationStates` caches that progress for admission/discovery in the same transaction; a disagreement with an existing job fails closed. Cleanup validates both participant state and the exact job before deleting, including completed shortcuts. Withdrawal updates state with merge semantics, preserving initial-study and historical facts while closing permission. A stale job cannot delete new participation. Batches allow up to 100 deletes plus run projections and two progress writes (at most 202 writes); size failures still shrink the batch.

Participant-facing history projects only consent/withdrawal events; Admin can inspect retained runs and operation receipts even after physical research deletion. Missing observations remain missing, and presentation permission never proves human viewing.

Each scheduled sweep shares one 40-second work budget across discovery and at most eight participants, leaving headroom under the 60-second Cloud Run limit and 75-second Scheduler attempt deadline. Pass the same absolute deadline into every participant's cleanup; never renew it per participant or transaction retry. Check it between reads and before buffering deletion writes. When the budget is exhausted, preserve committed progress and resume from the durable cursor on the next invocation. Participant withdrawal requests use a five-second work budget measured from handler entry. Web allows 45 seconds for withdrawal responses to accommodate cold start and caller checks before that budget begins. Once withdrawal is committed, unfinished deletion returns `WITHDRAWAL_CLEANUP_PENDING`; retries and scheduled cleanup resume the same history and progress. The budget prevents starting more work; it does not cancel an already in-flight Firestore RPC or commit, so it is not a hard network timeout. Never detach in-flight writes with a timeout race; await their outcome before returning or reporting committed progress. Aggregate counts describe attempted candidates, not the remaining queue size.

## Exact survey retries

The same `analysisId`, complete owner tuple and canonical content returns success without overwriting original data/timestamps. Compare object keys independently of order while preserving array order, JSON types and field presence. Different answer or analysis content conflicts. Completion metadata and submitted answers require their stored `_integrity` receipts; missing receipts are rejected rather than reconstructed from flat fields.

Completion requests require `analysisWorkspaceVersion`, a nonempty string of at most 128 characters captured by Web when the analysis starts. Support validates it through the canonical shared request schema and stores it in both the analysis/questionnaire record and `_integrity.metadata`. It participates in exact retry comparison: a changed version returns `ANALYSIS_COMPLETION_CONFLICT`, even after answer submission. Ordinary and administrator-recovered answers retain the original completion metadata and version. Support never substitutes its own deployed version or a version from answer submission. Missing versions are rejected without compatibility defaults. This is research metadata; withdrawal deletes it with the research record rather than copying it into retained operational projections.

New submissions use a strict `questionnaire: { kind, definitionId }` reference and nested `answers` map. The definition ID and every answer (including explicit null/empty values) participate in retry comparison; changed references conflict. Every completion metadata field participates in exact retry comparison. Top-level `surveyVersion` is rejected; questionnaire identity belongs to the subsequent strict questionnaire reference. Consent, ownership, withdrawal, reserved-key and payload-shape checks still apply.

Support does not load questionnaire definitions. Web validates required answers and copies the displayed definition's canonical hash and kind into the request. Survey acceptance does not contact Cloud Storage; verified archive registration is required before Web bundle distribution. The required nonempty string `survey_version` in [questionnaire JSON](../../../docs/examples.md#questionnaire-definitions) is definition metadata and is not sent as top-level completion metadata. Preserve `required: true` enforcement in the Web UI and Web server validation.

## Analysis observations

An analysis ID remains reserved while its operational run is retained, including after withdrawal physically deletes the research attempt. A new start with that ID returns `ANALYSIS_EVENT_CONFLICT` without changing retained history or the current study claim. Exact start retries with the original research attempt remain idempotent.

Store strict consent-bound start, terminal, presentation and output-loss observations only: PID, owner/consent IDs, timing and numeric measurements, never document names, bodies, results, prompts or raw errors. Require stored start before terminal/completion metadata, and completed attempt/metadata before presentation. `presentationRecordedAt` is set once on both attempt and questionnaire; exact retries retain it. It permits browser display after acknowledgement but cannot prove actual viewing. Ordinary initial survey submission requires that presentation record; [reviewed recovery](#administrator-recovery) has a separate authorization path. Acceptance preserves first `submittedAt` and sets `initialSurveyAcceptedAt` and follow-up eligibility in the same transaction.

The initial attempt/browser claim is transactional across server/client owners. One initial attempt can run; confirmed failure/cancellation before presentation releases its claim. Completed/presented/unconfirmed initial work blocks replacement attempts and other-browser authentication until accepted initial answers or researcher recovery, except for confirmed output loss before presentation. Follow-up sessions in separate browsers may execute concurrently. Missing/expired execution evidence is never assumed failed. Historical exact retries cannot release or replace a newer initial claim. Study state determines eligibility directly; authentication always returns its required `questionnaireKind`. Start requests contain no caller-selected kind: the attempt transaction derives and stores it from current study state and returns it. Exact start retries return the originally recorded kind even if eligibility has advanced, without rewriting the receipt or acquiring a new claim. Accepted initial answers end the initial flow independently of browser result availability or historical counts; no historical survey-count reconstruction is performed. Admin maintains separate operational aggregates.

An owner-bound `unavailable` observation with reason `result_unavailable` records output loss. Web requires an absent RAM job and either durable completion evidence or demonstrably abandoned Linux execution ownership; missing evidence alone is insufficient. Support requires the acknowledged start and current consent, then transactionally checks attempt/questionnaire presentation and submission. A presented initial result awaiting answers rejects loss recovery; follow-up output or an initial result whose answers were accepted may recover after presentation. Frozen uncertain survey submissions must reconcile by exact retry first. See [Web recovery guards](../../web/docs/analysis-coordination.md#completion-retry-and-inference-retry).

The transaction adds first `resultUnavailableAt` and the observation, marks existing questionnaire metadata, and releases only a matching unpresented initial claim without rewriting starts, outcomes, terminal timing or metadata. A missing terminal acknowledgement does not prevent loss recording or establish failure/completion; later terminal recording can preserve the original execution facts without affecting a newer claim. Exact loss retries retain the timestamp and cannot release another attempt. Recovered attempts reject new starts, completion metadata and presentation. Concurrent first presentation and loss cannot both commit. After the first presentation, no ordinary replacement initial analysis is allowed until accepted initial answers; delays, failures and earlier recovery remain in research history.

Historical terminal delivery is a distinct processing path. A currently authorized service caller may record only the outcome and occurrence/receipt times of an existing, originally authorized owner-matched run after withdrawal, an unused recovery grant or generation replacement. Validate retained consent/start evidence; exact receipt retries preserve first time and conflicting terminal claims fail. This path never creates an unknown run, restores measurements/answers, releases a replacement initial claim or changes current participation. Normal research writes still require current consent/generation. Web persists the strict audit-only terminal projection before ordinary terminal delivery and redelivers it after restart. This protects queued observations, but cannot recover an outcome lost before enqueue or after loss of the retained volume. See [retained Web audit queue](../../../docs/study-operations.md#retained-web-audit-queue).

## Indexes and retention

[Terraform](../../../infra/terraform/README.md) owns database/index/field configuration. Keep pseudonym and submitted-survey queries indexed while exempting arbitrary answer payloads. Authentication/information expiry and hashed Support rate-limit counters have explicit TTL policies; their asynchronous removal is not authorization. Gmail sent-message retention and operational logs are separate from Firestore withdrawal deletion.

## Coordinated updates

Preserve current consent, attempt, survey and audit facts; update Support, Web, Admin and contracts together. Follow [coordinated updates](../../../docs/study-operations.md#coordinated-updates) for current-schema sessions and grants. Missing infrastructure policies use the separately authorized [field recovery procedure](../../../infra/terraform/README.md#recovery-after-external-policy-deletion). Incompatible cloud states fail closed; do not fabricate missing ownership, receipt, outcome or history. Application rollback cannot undo accepted writes or recovery authorizations.

## Server-owned data purpose

The selected private profile's `participants.testEmailAddresses` is projected only to Support. Email-confirmation issuance uses normalized exact mailbox matching to fix `dataPurpose` (`research` or `test`) on the authentication record before sending mail. Resends preserve the original value even if configuration changes. Confirmation copies it to consent and participant state; missing/invalid values become `unclassified`. Attempts, survey metadata and withdrawal events inherit the validated consent's purpose in the same transaction. Completing attempts or submitting answers preserves the stored value and exact request receipts.

Clients cannot supply or overwrite `dataPurpose`: strict request schemas reject it, and extensible survey schemas reserve the name at every depth. Purpose is not part of participant identity and does not change pseudonym-wide counts, withdrawal or replay fences. Researcher test accounts must never be used as research participants. No addresses are added to Firestore or research snapshots by this classification.

## Administrator recovery

Consent requests fix `expectedRecoveryId` and `expectedStudyGeneration` alongside `expectedWithdrawalId` before dispatch. First issuance and pending resends reject a changed grant or generation before rate-limit writes and mail delivery. Pending verification checks the same boundaries before reporting that confirmation is still pending. An exact completed resend remains an acknowledgement only while its proof is current. The state-only lookup returns `studyGeneration`; Web and Support must use the updated strict contract together. Existing prepared requests without these fields require renewed consent preparation.

See [study operations](../../../docs/study-operations.md) for the three destinations and operator procedure. An unconsumed grant fences ordinary consent-bound writes until renewed authentication. Withdrawal remains available through the current confirmed consent. Issuance and consumption verify the durable recovery history record against the state pointer and validate the grant's expected study generation and withdrawal boundary; replacing a grant fences its earlier links. Confirmation consumes it in the same transaction as new consent and owner binding.

Initial-survey recovery requires an existing owner-matched completed initial attempt and completion receipt without accepted answers. Consumption binds its ID to the new initial claim; it never recreates deleted metadata or changes the original owner/presentation timestamp. Submission accepts a different owner only for that consumed grant, target and current confirmed consent. It writes `recoverySubmission` (recovery/new consent/client/server IDs) separately, preserves first accepted answers/timestamps and advances eligibility only once. A reviewed grant can authorize questionnaire entry without a presentation permission timestamp; the audit remains distinct from actual display evidence.

### Audit-only terminal redelivery

`POST /api/participant/analysis-outcome` accepts only owner IDs, analysis ID,
completed/failed/cancelled outcome and `endedAtMs`. Caller authorization and server
scope apply as for ordinary analysis operations. The transaction requires the
retained acknowledged start, matching full owner and original confirmed consent,
study generation and withdrawal boundary. Exact retries retain the first server
receipt. Conflicting outcome/end times return 409. Historical acceptance after
withdrawal/recovery updates only operational run/receipt records; no research,
claim, eligibility or questionnaire is recreated. Ordinary current terminal
delivery can subsequently save its RAM duration while retaining that receipt.
Output-loss recording also preserves an already accepted audit outcome and its
first receipt, even if ordinary terminal delivery has not yet saved the duration.

Authentication retirement also retains `retiredAt` and `withdrawalId` in its
business audit event, distinguishing the original authentication time from the
later retirement and its withdrawal boundary. Active verifiers/nonces are not
copied into the retained projection.

## Recorded document originals

Consent request, pending confirmation and accepted consent retain the same required `documentSet: { version, sha256 }`. Successful email confirmation records the server acceptance time with that reference; resends cannot relabel it. Withdrawal retains its first accepted reference, timestamp and linked consent even when a later retry presents another set. These records have no TTL and survive research deletion.

The scoped `/api/participant/document-original` read validates the requested PID, exact participation record and PDF purpose, then verifies the recorded manifest and original in the selected project's private archive. It permits an owned historical receipt after withdrawal and requires no current participation mutation. Web remains responsible for its authenticated session/owner check. Local/emulator execution never falls back to real cloud storage. Consent confirmation, withdrawal acceptance and research cleanup perform no archive reads or PDF generation. There is no Firestore document-set registry; see [document sets](../../../docs/document-sets.md).
